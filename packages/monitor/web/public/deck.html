stoke Finding out where Claude Code money actually goes, and stopping the part that is wasted.

What I was trying to solve

Claude Code tells you the total. It does not tell you what the total bought.

Spend is visible only after the fact, as one number, with no way to tell the part that did real work from the part that was pure overhead. If you cannot separate the two, you cannot reduce either.

  • Which projects are expensive, and why those ones
  • Which charges were avoidable, and what to do instead
  • Whether a change you made actually helped
Why the money leaks

Most of the bill is holding the conversation, not answering.

Claude re-reads the whole conversation on every message. Cached, that is cheap. Let the cache go cold and the next message pays to rebuild all of it at full rate.

0.1xreading a warm cached conversation
1.25xrebuilding it after the window closes
5xwhat Claude writes, against what it reads

So one coffee break can cost more than the work either side of it, and a long session pays for its dead history on every single message.

The approach

stoke: two engines behind one command.

Engine 1, prevent

Keep-alive proxy

Sits in front of the API. Before a conversation's cache window closes it sends a ping that produces no output, so the conversation stays warm while you are away and the next real message pays the cheap rate instead of the rebuild rate.

Engine 2, measure

Monitor and dashboard

Reads every transcript into a local database, prices each turn against the real rate card, and runs detectors that name each avoidable charge in plain language. Nothing leaves the machine.

What it finds

Five causes, each named in words you can act on.

  • You walked away and the cache went cold.Idle past the window, so the next message rebuilt the conversation from scratch.
  • Replies were longer than the task needed.Output costs about five times what input does, so verbosity is the most expensive habit there is.
  • Instructions were edited mid session.Changing CLAUDE.md or settings while a session runs throws away everything cached for it.
  • Sessions ran near the context limit.Every new message re-bills all the dead history behind it.
  • A top-tier model did mechanical work.Bulk searching and file sweeps do not need the most expensive model.
What it does about it

Six automatic steps, from a nudge to a refusal.

  • Adds cost rules to every session.Be brief, do not re-read files already in context, hand bulk searching to a cheaper model.
  • Warns before a conversation goes cold.So you know the next message will pay the rebuild rate, before you send it.
  • Warns when a session grows too large.
  • Blocks a message from an oversized session outright.The only step with a certain payoff. It refuses and asks for a compact first, rather than suggesting something.
  • Stops a full re-read of a file it already has.Redirects to the part actually needed.
  • Records what every session cost.So the next question about spend has an answer.
What happened

Measurement changed behaviour more than automation did.

  • Naming the cause in plain language was the whole product."You walked away and the cache went cold" is something you can act on. A row reading cache_expiry is not.
  • Refusing beats suggesting.The hard block on oversized sessions is the one lever whose saving is certain, because nothing has to be believed for it to work.
  • The first dashboard was unreadable.Over a thousand rows and a negative number as the headline. Built for the person who wrote it, not for anyone seeing it once.
  • I nearly cut the part that was making money.Most keep-alive spend goes to sessions that never come back, which reads like waste. It is not: a rebuild avoided is worth many times a ping, and roughly half of idle sessions do come back.
What I would do differently

Price the counterfactual, not just the cost.

  • What something costs is easy. What it bought is the real question.Totalling the spend on a feature took an hour. Working out what it prevented reversed my conclusion about it.
  • Judge a bet by its odds, not by its losing half.Counting only the losses makes a profitable gamble look like a leak.
  • Test against live data, not fixtures.Two bugs passed every unit test and only appeared against a real database.
  • Write the numbers for a stranger from the start.The rewrite that made the readout understandable cost more than the original build.
Running it

Local, single command, nothing shared.

// once per machine
npm run setup

// starts the proxy and the monitor together
npm start

// the dashboard
http://localhost:5599

Thresholds and each automatic step can be set to watch, warn, or enforce in ~/.stoke/config.json. The database, the transcripts and the figures stay on the machine that produced them.
